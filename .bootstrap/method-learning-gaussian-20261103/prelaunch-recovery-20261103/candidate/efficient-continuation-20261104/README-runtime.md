# Native runtime adapter candidate

This source is inactive until the owning coordinator has qualified and launched it. Its CLI is:

```
python runtime.py --study ABSOLUTE_STUDY --arm exploration --operation run|recover \
  --source-sha256 RUNTIME_SHA --status-path OWNED_COMMAND/RUNTIME_STATUS.json
```

The study must be a canonical direct child of this repository's `.scratch/studies`. The status file must be inside a canonical existing `.bootstrap/.../commands/000000` directory created by the owning command. The coordinator authenticates the whole history, native implementation, goal contract, deployment and resource profile. At runtime startup this adapter checks its own source, frozen diagnostic source, and the diagnostic's fixed small native source list; importing it does not invoke the full implementation/dependency hashing routine.

`RuntimeArm` subclasses the unchanged native `Arm`. It inherits native `run`, `_research_round`, mathematical acceptance, kernel/axiom/English correspondence checks, receipt consumption and cost accounting. Fresh requests and their arguments are passed unchanged. The ordinary controller lock and stop-signal protocol are retained. The adapter never clears `STOP.json`, adds a new paid retry identity, refunds a charge or edits a saved plan/request/receipt.

For a **main** research round with an existing numeric researcher receipt, the adapter requires a retained accepted planner result from one of the native bounded repair/generation paths. The unchanged native planner validates that exact chain. A closed researcher cannot cause a new proposer invocation. The frozen diagnostic's order-restoration routine then tries the original researcher request order and its inverse, accounting for `reverse_portfolio`. It accepts only an unchanged canonical staged digest and **the exact full original regenerated researcher request, including `program_execution.input_hash`**. The commitment remains unchanged. This changes an in-memory map order only. A main round with no researcher receipt uses the ordinary fresh path. Other request constructors, including policy comparison branches, retain native exact matching; the adapter does not strip their additional fields to force a match.

A numeric failed researcher receipt follows the unchanged native failure bookkeeping. A completed receipt follows the unchanged native report acceptor and its per-item `ADMITTED.json` transactions. The adapter neither interprets a payload as a proof nor replaces an acceptance check. Partial validation artifacts remain at their original locations. A later attempt may use the native journal's exact before-state and source checks; an incompatible stage refuses through the normal native checks.

Cheap native `headroom(limits())` checks run before expensive qualification and before every paid call. Only the exact exceptions `admission_disk_headroom` and `admission_memory_headroom` cause a 15-second wait, with a stop check before every attempt. Unknown observer/cleanup failures fail closed. A source-bound public status file reports `waiting_host_headroom` while the coordinator's owning phase may still be `research_running`; it changes back to `running` when the floor is restored. It contains only source, study, operation, timestamp, phase and an optional fixed admission reason. It contains no payload, process identifier or liveness assertion. The owning command's numeric exit remains the authority for process completion.

If one of those exact admission exceptions interrupts native execution, the adapter reloads the durable native state rather than resetting counters or using modified in-memory bookkeeping. Before retrying, it requires authenticated numeric closed receipts for any active or unregistered job. Missing receipts or unknown effects refuse before native recovery can inspect a saved PID or manufacture a nonnumeric uncertainty. An unregistered nonnumeric receipt is refused. Already registered historical nonnumeric dispositions remain byte-bound in their original registry and continue to depend on the coordinator's existing source-qualified history verification. They receive no new disposition here. A watchdog's failed `disk_headroom` receipt is data for the native failed-result branch; it is not permission to rerun the paid role.

`RUNTIME_STATUS.json` uses schema `math-gkm.efficient-runtime-status.v1`, with `source_sha256`, `study`, `operation`, `phase`, `updated_at`, and optional `resource_reason`. Phases are `running`, `waiting_host_headroom`, `finished`, `refused`, and `stopped`. This file records an observation, not a proof or a live-process claim. Runtime stdout similarly reports `root_proved: false`; only the owning full-root and English correspondence gates may declare the research goal achieved.

`test_runtime.py` uses temporary neutral fixtures and forbids subprocess launches. It covers fresh call identity, actual native cached planner/repair/generation validation, exact and inverse order restoration, unrelated-field refusal, no fresh replanning of a closed researcher, failed and completed native result paths, an interrupted completed-report per-item journal recovered without revalidation or recharge, receipt uncertainty/cleanup refusal, cheap checks before expensive/paid work, stop handling, and public status. Source tests prove the adapter inherits native `run` and `_research_round` and does not invoke the full identity routine during import or small source verification. These are operational tests; they contain no advice for the mathematical problem and run no actual research or compilers.
