# Inactive generic prelaunch recovery candidate

These files are proposed source changes only. They have not been installed in `machinery`, have not changed any study, and have not launched a model, Lean process, or new proof. The original historical recovery handler is retained byte for byte apart from its private function name. No theorem statement, research strategy, mathematical hint, frozen research budget, or resource floor changes.

## The permitted operation

A native recovered proposer receipt can truthfully say `uncertain_effects_not_replayed` without a numeric return code. This candidate preserves that receipt, its complete ordinary reservation, and its original counted identity. Only a separately recorded operator observation proving the failure occurred at a native protocol event before watchdog `Popen` permits one distinct identity, `plan-NNNN-repair-1`, through the existing `Arm.plan_with_repair` loop and `proposal_repairs` allowance. The new repair has the same model, reasoning effort, seconds, workspace and readonly proposer role; ordinary native accounting applies. A missing or uncertain repair result cannot authorize another recovery identity or another planning generation. Unknown effects after watchdog creation remain a refusal.

The source handles all nonnegative logical indices, including indices longer than four digits, and either public arm. It does not contain a problem-specific or plan-0007-specific permission. Original job files are limited to spec, request, prompt, recovered receipt and the immutable consumption marker. Even an empty watchdog or worker artifact refuses this lane.

## Grant and source provenance

The new protected authorization pointer is `prelaunch_recovery: {path, sha256}`. The existing `operational_recovery` pointer and historical handler remain separate. The new grant schema is `math-gkm.closed-prelaunch-proposer-recovery.v1`; exact fields are `PRELAUNCH_FIELDS` in the candidate. Its `revision_core`, schema `math-gkm.prelaunch-source-revision.v1`, binds every identity in `PRELAUNCH_CORE_FIELDS`, the observation SHA, and an archived old-seal pointer. `revision_binding` is the canonical JSON digest of this core. The new study seal must bind the exact actual implementation, the grant path/core binding and the old-seal SHA. Current authorization and state must agree with that genuine new seal. An independently performed new deployment preflight is required by unchanged native deployment checks; this file does not manufacture it.

The projection binds research, counters, reservations, funded pools, counted jobs, receipt registry, round/phase, active state, resolution, and durable protocol state, attempts, reserved/observed seconds and semantic/host event lists. Only the lifecycle status is normalized to `running`, as the existing native run loop sets that tag before planning. The original stopped-state SHA remains in the revision core. The complete pre-repair source inventory is also bound. This is permission to consume an existing allowance, not to refund an earlier request or enlarge a quota.

The observation schema is `math-gkm.closed-prelaunch-proposer-observation.v1`. It requires actual numeric owner/native command closure and native-recovery closure references; no worker/model launch; verified cleanup; and protected, bounded archived source, trace and original-log pointers. The archived old seal authenticates the old implementation and old `study.py` SHA. The exact trace excerpt must occur in the retained native log. The traceback must name the actual `Arm.call` event line, which an AST inspection verifies is before the first `subprocess.Popen` in that same archived function. Host observations remain explicit trusted operator evidence; this does not claim a Lean proof of operating-system behavior.

`validate_prelaunch_evidence(grant)` is the pure validation API for staged revision tooling. It returns only the observation/source/trace hashes and writes no marker, counter or role data. The live planner path additionally checks current source/seal/grant authority, original immutable job bindings, the unique charge and settled protocol state before recording consumption. Current-stage accounting checks must not be applied blindly to a historical state after later research advances: later continuation needs its own source-qualified verifier for this exact historical nonlaunch record, without replacing its absent numeric return code.

## Bounded pure protocol retry

The bridge candidate allows at most two attempts at a pure Lean protocol transition. Each attempt reserves the original 30 seconds and increments the existing separate protocol-attempt counter before execution. The original total allowance `4*max_calls+2`, unchanged headroom admission and immutable resource limits remain in force. A retry occurs only after the existing explicit protocol rejection, with unchanged guard, semantic-event list, active intent, command and protocol source hashes. The protocol state is committed once after success. Failed and successful elapsed times are both charged to the observed protocol duration. This is not a retry of any proposer, model, watchdog or researcher. Source/input changes, an exhausted allowance or failed headroom admission stop it.
